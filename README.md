# lost-found-city-bot
# Бот для поиска потерянных вещей в городе («Lost & Found City Bot»)

Сервисный Telegram-бот, предназначенный для автоматического сопоставления объявлений о потерянных и найденных вещах на основе категорий, геопозиционирования (радиус 1–2 км) и временного интервала (±2 часа).

---

## О проекте и архитектуре

Миллионы вещей (ключи, телефоны, документы) теряются ежедневно. Информация в социальных сетях разрознена, а поиски вручную занимают много времени.

**Принцип работы бота:**

* **Нашедший** — отправляет фото, категорию и геолокацию. Бот присваивает вещи уникальный ID и публикует объявление в публичном Telegram-канале.
* **Потерявший** — указывает категорию, время и место потери.
* **Автоматическое сопоставление** — бот производит поиск по пересечению трех параметров: **категория + георадиус (1–2 км) + время (±2 часа)** и выдает ссылку на контакт нашедшего.

## Технологический стек

* **Язык программирования:** Python 3.11
* **Bot Framework:** `aiogram 3.x` (Asyncio)

* **Тестирование:** `pytest`, `pytest-asyncio`
* **Контроль версий & Управление:** Git, GitHub, Redmine

## Правила работы и регламент команды

Все участники команды обязаны строго придерживаться единых стандартов разработки, описанных ниже.

### Соглашение по именованию веток в Git

Запрещены прямые коммиты в ветки `main` и `develop`. Разработка ведет по схеме Git Flow:

1. **`main`** — стабильная продуктовая версия кода.
2. **`develop`** — основная ветка разработки и интеграции готовых фич.
3. **`feature/`** — создание нового функционала.
*Пример:* `feature/add-location-search`, `feature/photo-upload`.
4. **`bugfix/`** — исправление выявленных ошибок.
*Пример:* `bugfix/fix-geo-matching`, `bugfix/fix-time-filter`.
5. **`hotfix/`** — срочные исправления для ветки `main`.

---

### Правила написания и комментирования кода

1. **Стандарт стиля:** Код должен строго соответствовать стандарту **PEP8**. Перед отправкой PR код проверяется линтерами (`flake8`, `black`).
2. **Аннотация типов (Type Hints):** Обязательна для всех сигнатур функций, обработчиков и методов работы с базами данных:
```python
async def find_matches(category_id: int, lat: float, lon: float) -> list[Item]:
    ...

```


3. **Комментирование:**
* Документирование функций и классов выполняется через docstrings на русском языке.
* Комментарии должны пояснять **логику и причины** нестандартных решений (например, формула вычисления георадиуса в PostGIS), а не пересказывать очевидный код.



---

### Процедура Code Review и слияния (Merge Requests)

1. **Создание Pull Request (PR):**
* PR создается из рабочей ветки `feature/*` или `bugfix/*` в ветку `develop`.
* Заголовок PR должен содержать номер задачи из Redmine и краткую суть: `#12: Добавить поиск вещей по радиусу 2 км`.


2. **Назначение проверяющего (Reviewer):**
* Ни один PR не может быть влит без проверки вторым разработчиком.
* *Адинцов А.* проверяет коммиты *Аккизова М.*
* *Аккизов М.* проверяет коммиты *Адинцова А.*
* *Семенов К.* проводит финальный ревью и принимает PR.


3. **Условия слияния (Merge):**
* PR успешно проходит автоматические тесты (`pytest`).
* Получена одобрительная отметка **«Approved»** от проверяющего.
* Слияние выполняется кнопкой **Squash and Merge** для сохранения чистоты истории Git.
